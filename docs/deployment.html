Deploying the docs site

The docs/ directory serves two surfaces: the offline viewer bundled in the binary (zreview docs) and an online copy. This page covers the online copy.

One source of truth

Every HTML and CSS file under docs/ is embedded in the Go binary via //go:embed *.html *.css in docs/embed.go. The same files are what the hosting workflow uploads. Any edit updates both surfaces. No build step, no bundler, no framework.

Picking a host

Cloudflare Pages is the default because it works with a private repo on the free tier. If the repo flips to public, GitHub Pages activates automatically alongside it — both deploys can coexist.

Cloudflare Pages: one-time setup

1. Create the Pages project

From any machine with node:

npx wrangler login
npx wrangler pages project create z-code-reviewer --production-branch=main

wrangler login opens a browser to authorize. The project create command needs to run only once — it registers the project name in your Cloudflare account. The public URL will be https://z-code-reviewer.pages.dev/.

2. Create an API token

In the Cloudflare dashboard: My Profile → API Tokens → Create Token → Cloudflare Pages: Edit. Scope it to the account and to the z-code-reviewer project only.

3. Add repo secrets and the enablement flag

In GitHub, on this repo:

  • Settings → Secrets and variables → Actions → New repository secret
    • CLOUDFLARE_API_TOKEN — the token from step 2
    • CLOUDFLARE_ACCOUNT_ID — visible in the Cloudflare dashboard sidebar
  • Settings → Secrets and variables → Actions → Variables → New repository variable
    • CLOUDFLARE_PAGES_ENABLED = true

The variable is a hard on/off switch. GitHub Actions can't reference secrets in job-level if: guards, so the workflow skips cleanly until you set the variable to true. That keeps CI green while you're still setting things up.

4. Trigger the first deploy

Any push to main that touches docs/** or .github/workflows/cloudflare-pages.yml triggers the workflow. You can also fire it manually via Actions → Deploy docs to Cloudflare Pages → Run workflow.

After the first successful run, the site is live at https://z-code-reviewer.pages.dev/.

Rolling back a deploy

Cloudflare Pages keeps every deploy. In the dashboard: Pages → z-code-reviewer → Deployments → pick a prior deploy → Rollback. No workflow re-run needed.

Custom domain (optional)

In the Cloudflare Pages dashboard: Custom domains → Set up a custom domain. If the domain is already on Cloudflare, DNS is one click. Otherwise add the CNAME manually. HTTPS is issued automatically.

Disabling the deploy

Two ways, ranked by scope:

  • Flip CLOUDFLARE_PAGES_ENABLED back to false in repo variables — workflow skips silently, project stays in Cloudflare.
  • Delete the project in the Cloudflare dashboard — workflow errors on the next run until re-enabled.

If the repo goes public

The pages.yml workflow is gated on !github.event.repository.private. The moment the repo flips public, that workflow starts deploying docs/ to https://shubam-disseqt.github.io/z-code-reviewer/ alongside Cloudflare. Nothing else changes.

Threat model note

The docs site is public read-only content. The Cloudflare API token is a write credential scoped to Pages only. Treat it like any other CI secret: rotate on suspected compromise, never commit, never surface in logs. See Security and THREAT_MODEL.md for the full picture.
