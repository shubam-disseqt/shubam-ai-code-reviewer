---
title: Index and Context
description: How sacr assembles the codebase-context block for each review from the always-on per-repo index.
---

The reviewer needs to know more than the diff: what the changed
function calls, who calls it, what conventions the repo enforces. That
signal comes from one of two paths.

## One index, always on

Every repo gets its own SQLite index at
`~/.sacr/index/<sha256(abs repo path)[:16]>.db`. `sacr review` opens it
on every run — there is no flag to turn it off and no setup step.

During a review, stage 3 checks which changed files have no summary row
yet and summarizes them right there on the cheap tier, before the
reviewer sees the diff. The reviewer then pulls per-file summaries,
symbol maps, and blast-radius rows from the index and stitches them into
the prompt. Where the index is still thin (files the PR doesn't touch,
fresh clone), the tool loop's `file_read`, `file_find`, and `code_search`
fill the gaps on demand.

`sacr index --repo .` pre-warms the whole repo so cross-file context is
complete from the first review. It is a speed-up, not a prerequisite.

## What gets indexed

Not every file. The indexer walks the repo with the same filter used
by the review selector, so generated files, vendor dirs, lockfiles,
and binary blobs are skipped.

- **Per-file summary.** One LLM call per eligible file: exports, key
  types, dependencies, one-paragraph purpose. Cached by content
  hash — unchanged files skip on the next incremental pass.
- **Symbol map.** Cheap heuristic extraction of top-level declarations
  (functions, types, constants) per language. Used for the "who else
  touches this symbol" lookup during review.
- **Conventions.** A short list of repo-scoped idioms detected from
  the codebase — error style, logger of choice, testing framework.
  Injected into the review prompt to keep suggestions consistent with
  what the repo already does.
- **Manifests.** `go.mod`, `package.json`, `Cargo.toml`, and similar
  dependency files, so the reviewer knows what's in scope without
  re-parsing them.

## SQLite vs Postgres

`SACR_DB_URL` overrides the default location and accepts two DSN shapes:

| DSN | Backend | When to use |
|---|---|---|
| `sqlite:///path/to/index.db` | Local SQLite file | Single-machine, one-repo case. CI runners that keep a persistent cache volume. The default choice. |
| `postgres://user:pass@host:5432/db?sslmode=require` | Postgres | Shared index across many reviewers — team CI where every runner should reuse the same summaries. Higher operational cost. |

The schema is identical either way. Migration paths from SQLite to
Postgres are one-shot dumps and imports; there is no built-in
migration tool because most teams settle on one or the other and stay
there.

<Callout type="info">
  **Postgres note.** Point every reviewer at the same database.
  Concurrent `sacr index` runs are safe — the indexer uses row-level
  insert-or-update, not table locks — but you'll pay the LLM cost
  multiple times if two reviewers race on the same fresh file. In
  practice, run `sacr index --repo .` from one scheduled job and let
  reviews only read from the shared DB.
</Callout>

## Running the indexer

```bash
# pre-warm the whole repo (uses the per-repo default DB; set SACR_DB_URL to relocate)
sacr index --repo .

# subsequent runs — incremental (only re-summarizes changed files)
sacr index --repo .

# force full re-index (schema bump, embedding-model change, etc.)
sacr index --repo . --full
```

Incremental indexing keys off the content hash of each file. If the
file bytes haven't changed since the last successful summary, the row
is reused. This is what makes a scheduled indexer cheap after the
first run.

## CI containers

The GitHub Action runs `sacr` in a fresh container, so the default index
lives and dies with the job. Only the PR's changed files are summarized
each run — a few cheap-tier calls. To carry the index across runs, mount
a cache volume and point `SACR_DB_URL` at a file on it.

## Cost model

Two distinct model roles, priced separately:

| Env | Called when | Sensitivity |
|---|---|---|
| `SACR_MODEL` | Every review invocation, once per changed file (main task loop). | High. This is where quality lives. Use a capable model. |
| `SACR_INDEX_MODEL` | Once per file at index time (per-file summary + embedding). Cached until content changes. | Low. A cheap embedding-class model is usually fine. |

## Common issues

- **Index looks empty after a run.** Check that the walker's filters
  didn't skip everything. `sacr index -v` logs per-file decisions.
- **Cross-file suggestions still weak.** The symbol map is heuristic
  and language-specific. If a repo uses non-standard extensions,
  extend the file-type detector.
- **First review of a repo is slower.** Expected — every changed file
  is summarized once. Run `sacr index --repo .` to pre-warm.
- **Postgres connection errors.** Verify `sslmode` matches what your
  Postgres server expects. Most managed Postgres accepts
  `sslmode=require`.
