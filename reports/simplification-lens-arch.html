sacr feature design

Simplification lens — architecture

A second review lens that hunts code to delete or inline — the opposite polarity of the existing Suggestion Mode. Delivered as one prompt file, one config bool, and one conditional string append. No schema, no tool, no scoring, no emit path change.

File Action Why

docs/configuration.html UPDATE Document simplification.enabled flag.

5. Why this shape (design rationale)

  • One config bool, one conditional string append. Pipeline already composes system content from N optional blocks (reviewctx, known_issues). The simplification lens is block N+1. No new abstraction.
  • No new category. Reusing maintainability + a text tag means the finding rides every existing rail — scoring, filter, emit, GitHub rendering, fingerprint, carryover, effort table — for free.
  • No new tool. code_comment already carries existing_code + suggestion_code, which is exactly what a "delete this / inline to X" finding needs.
  • Failure modes are already handled. Bad JSON → comment_args_repair. Bad line → ResolveComment → RelocateAcrossFiles → ReLocateComment. Low-confidence noise → --min-severity=medium.

6. Risks (from the plan §8)

Risk Likelihood Mitigation
False-positive suggestions (interface with a hidden second impl) Medium Prompt says "if unsure, do NOT emit — deletion is destructive." Default-off adds a second safety valve.
Contradiction with Suggestion Mode ("extract" vs "inline" on same block) Medium Explicit prompt rule: the simplification lens wins on the same anchor. Example pair in the prompt.
Cap contention with Suggestion Mode on shared 5/file budget Low Prompt orders lenses by priority (simplification first). If field data disagrees, add per-lens cap later.
Nit-storm on refactor PRs Low-Medium 5/file, 20/PR caps hold. Low-severity + non-blocking exit code → no CI breakage.
Reviewers dismiss simplification findings as opinion Medium Every finding cites concrete replacement (stdlib call, inlined body, deleted flag name) — same rule as Suggestion Mode.
